# PICON 고득점 페르소나 AI — 구현 로드맵

> 목표: PICON 평가에서 IC / EC / RC 세 축 모두 인간 기준선(IC 0.90, EC 0.66) 이상 달성

---

## 1. 과제 구조 재정리

### PICON 평가 메커니즘 (picon-eval 0.1.3 기준)

| 단계 | 에이전트 | 역할 |
|------|---------|------|
| 인터뷰 생성 | Questioner (GPT-5) | WVS 사전 질문 10턴 → 로직 체인 질문 40턴 → 재테스트 10턴 |
| 주장 추출 | Extractor (GPT-5.1) | 응답에서 검증 가능한 엔티티·주장 쌍 추출 |
| 사실 검증 | Web Search (GPT-5) | Serper API로 각 엔티티를 검색, 지지/반박/NEI 분류 |
| 점수 산출 | Evaluator (Gemini-2.5-Flash) | IC / EC / RC 점수 계산 |

**실행 모드**: 팀원 코드는 `api_base` 모드(외부 서버에 HTTP 요청). 대안으로 `model` 모드(persona 문자열을 시스템 프롬프트로 주입해 LLM 직접 호출)도 존재.

### 세 축의 수학적 구조 — 무엇을 최적화해야 하는가

```
IC = 2 × Cooperativeness × Non-contradiction Rate
     ─────────────────────────────────────────────
         Cooperativeness + Non-contradiction Rate
```
→ 회피 응답(모르겠어요, 말하기 싫어요) 하나가 Cooperativeness를 깎고,
  모순 응답 하나가 Non-contradiction Rate를 깎음.
  **조화 평균이므로 둘 중 하나라도 낮으면 전체가 낮아짐.**

```
EC = 2 × Coverage × Non-refutation Rate
     ──────────────────────────────────
         Coverage + Non-refutation Rate
```
→ Coverage = 검증 가능한 엔티티를 언급한 턴의 비율.
  **모호하거나 가상의 기관을 언급하면 Coverage↑ 이지만 Non-refutation↓.**
  **실존하는 기관·장소만 언급하면 둘 다 올릴 수 있음.**

```
RC = (초기 10문 답변) == (40턴 후 재테스트 답변) 비율
```
→ 확률적 디코딩이 주요 원인. **temperature=0 + 인구통계 질문 직접 매핑**으로 거의 1.0 달성 가능.

### 기존 프로토타입의 한계

1. **main_interrogation이 대부분 누락** — 실제 완전 평가(50턴)가 MaengMaengbot 1회뿐.
2. **규칙 기반 파서(36개 정규표현식)** — 연쇄 질문(이전 응답의 논리적 함의에서 파생)에 매칭 실패 → IC 급락.
3. **Serper API 403 오류** — EC 검증이 작동하지 않음(점수가 0).
4. **LLM 없이 슬롯 룩업** — 협력도는 높을 수 있으나, 40턴 심문의 열린 질문엔 대응 불가.
5. **가상 회사(Hanbit Data)** — 웹 검색에서 발견 안 됨 → Coverage 낮음.

## 2. 핵심 설계 결정

### 2-A. 구현 모드 선택: `model` 모드 vs `api_base` 모드

| 모드 | 방식 | 장점 | 단점 |
|------|-----|------|------|
| `api_base` (외부 서버) | FastAPI 서버 배포 후 엔드포인트 제공 | 서버 내부 로직 완전 제어 | GitHub 배포 필요, 복잡도 높음 |
| `model` (시스템 프롬프트) | persona 문자열을 시스템 프롬프트로 전달 | 배포 불필요, 즉시 실행 가능 | 프롬프트 설계에 모든 것을 담아야 함 |

**결정: `model` 모드 채택 (단기), `api_base` 모드 준비 (중기)**

`picon.run(persona=..., model="gpt-4o", ...)` 한 줄로 테스트 가능하며, 프롬프트 엔지니어링만으로 빠르게 점수를 올릴 수 있음. 점수가 안정화되면 `api_base` 모드로 전환해 검증 파이프라인을 서버 내부에 구현.

### 2-B. 페르소나 데이터 소스: 실제 인터뷰 기반 + 웹 검색 검증

**범준 본인의 실제 인터뷰 기반**으로 팩트 시트 작성. EC 점수를 위해 다음 원칙을 따름:

- 언급하는 **모든 기관·장소는 구글 검색 1페이지에 노출되어야 함**
- 예: 학교, 직장, 거주 지역, 자주 가는 장소 등을 실존하는 것으로 기재
- **팩트 시트 작성 단계에서 웹 검색을 자동화**하여 각 엔티티의 실존 여부 검증
- 가상의 세부사항(예: 가상의 팀명, 가상의 프로젝트)은 검증이 안 되므로 Coverage에는 기여하지 않도록 설계

### 2-C. IC 전략: 기억 일관성 프롬프트

시스템 프롬프트에 다음 구조를 포함:

```
1. 팩트 시트 (고정 사실들)
2. 응답 원칙:
   - 모든 응답은 팩트 시트에 근거해야 한다
   - 모르거나 불확실한 경우에도 페르소나에 일관된 추론으로 답한다 (회피 금지)
   - 이전에 답한 내용과 절대 모순되지 않아야 한다
   - 새로운 세부 사항을 언급할 때는 팩트 시트와 충돌하지 않아야 한다
```

### 2-D. RC 전략: 결정적 응답 보장

- 인구통계 질문(나이, 직업, 학력, 가족, 거주지, 소득 등)에 대해 **팩트 시트의 값을 그대로 사용**하는 지시 추가
- `completion_kwargs={"temperature": 0}` 으로 greedy 디코딩 설정

## 3. 로드맵

### Phase 0 — 기반 데이터 수집 (현재 → 인터뷰 내역 수령 후)

| 작업 | 담당 | 입력 | 산출 |
|------|------|------|------|
| 0-1. 범준 본인 PICON 인터뷰 내역 수집 | 범준 | — | 인터뷰 Q&A 전문 |
| 0-2. 기존 PICON 점수 분석 | Claude | 인터뷰 내역 | 취약 턴 식별, 각 축별 점수 원인 분석 |
| 0-3. 팩트 시트 초안 작성 | Claude | 인터뷰 내역 | 범준 기반 `fact_sheet_beomjun.json` |

### Phase 1 — 팩트 시트 고도화 및 웹 검증 (1~2일)

| 작업 | 담당 | 세부 내용 |
|------|------|---------|
| 1-1. 엔티티 목록 추출 | Claude | 팩트 시트에서 검증 가능한 모든 기관·장소 추출 |
| 1-2. 웹 검색 자동 검증 | **Codex** | 각 엔티티를 OpenAI web_search로 검색 → 실존 여부 + 올바른 공식 명칭 확인 |
| 1-3. 팩트 시트 정제 | Claude + Codex | 검증 실패 엔티티를 실존 대안으로 교체 |
| 1-4. EC 최적화 엔티티 보강 | Claude | Coverage를 높이기 위해 검증 가능한 구체적 사실 추가 |

**Codex 명세 #1**: 팩트 시트 웹 검증 스크립트

### Phase 2 — 시스템 프롬프트 엔지니어링 (2~3일)

| 작업 | 담당 | 세부 내용 |
|------|------|---------|
| 2-1. 기본 persona 프롬프트 작성 | Claude | 팩트 시트 → persona 문자열 변환 |
| 2-2. IC 최적화 지시문 추가 | Claude | 회피 금지, 모순 방지, 사실 기반 지시 |
| 2-3. RC 최적화 지시문 추가 | Claude | 인구통계 질문 결정적 응답 지시 |
| 2-4. `model` 모드 로컬 테스트 | **Codex** | `picon.run(persona=..., model="gpt-4o", do_eval=True)` 실행, 점수 산출 |
| 2-5. 점수 분석 및 프롬프트 개선 | Claude | 취약 턴 분석 → 지시문 보완 |

**Codex 명세 #2**: model 모드 PICON 테스트 및 점수 산출 스크립트

### Phase 3 — 검증 파이프라인 구현 (3~4일)

| 작업 | 담당 | 세부 내용 |
|------|------|---------|
| 3-1. 응답 후처리 검증기 설계 | Claude | 모순 감지 로직 설계 |
| 3-2. 메모리 관리 모듈 구현 | **Codex** | 대화 기록에서 핵심 주장 추출 + 저장 |
| 3-3. 모순 감지기 구현 | **Codex** | 신규 응답이 기존 주장과 충돌하는지 LLM으로 검사 |
| 3-4. 재생성 루프 구현 | **Codex** | 충돌 감지 시 지시 보완 후 재생성 |
| 3-5. 통합 테스트 | Claude | 검증 파이프라인 포함 PICON 재평가 |

**Codex 명세 #3**: 메모리 + 검증 파이프라인

### Phase 4 — api_base 서버 전환 및 GitHub 배포 (4~5일)

| 작업 | 담당 | 세부 내용 |
|------|------|---------|
| 4-1. FastAPI 서버에 검증 파이프라인 통합 | **Codex** | Phase 3 로직을 서버 내부로 이식 |
| 4-2. temperature=0 강제 설정 | Codex | RC 보장 |
| 4-3. GitHub 배포 (Vercel/Render) | **Codex** | 기존 render.yaml/vercel.json 활용 |
| 4-4. `api_base` 모드로 전체 PICON 평가 | Claude + Codex | 공식 점수 산출 |

**Codex 명세 #4**: 서버 통합 및 GitHub 배포

### Phase 5 — 점수 최적화 (5~7일)

| 작업 | 담당 | 세부 내용 |
|------|------|---------|
| 5-1. 점수 취약 턴 분석 | Claude | JSON 결과 파일 분석, 모순/회피/반박 발생 패턴 |
| 5-2. 팩트 시트 보강 (Coverage↑) | Claude + Codex | 검증 가능한 사실 추가 |
| 5-3. 프롬프트 A/B 테스트 | Codex | 여러 프롬프트 변형 자동 테스트 |
| 5-4. 최종 점수 측정 | 전체 | 목표: IC > 0.90, EC > 0.66, RC > 0.85 |

## 5. 기술 스택 및 제약

| 항목 | 선택 | 이유 |
|------|------|------|
| 인터뷰 응답 모델 | GPT-4o (또는 o4-mini) | OpenAI API 사용 가능, 긴 컨텍스트 |
| Questioner/Extractor | GPT-5 / GPT-5.1 | picon-eval 기본값 (변경 없음) |
| Evaluator | Gemini-2.5-Flash | picon-eval 기본값 (변경 없음) |
| 웹 검증 | OpenAI web_search (Phase 1) / Serper (Phase 4+) | Serper 키 없을 경우 OpenAI 활용 |
| 배포 | Vercel (Serverless) | 기존 인프라 활용 |
| 팩트 시트 포맷 | picon_fact_sheet_v2 (JSON) | picon-eval 호환 |

## 6. 인간 기준선 대비 목표 점수

| 축 | 인간 기준선 | 기존 최고 AI (Character.ai) | 우리 목표 |
|----|-----------|--------------------------|---------|
| IC | 0.90 ± 0.05 | ~0.70 (추정) | **≥ 0.88** |
| EC | 0.66 ± 0.07 | 0.71 ± 0.07 | **≥ 0.65** |
| RC | (측정 중) | 0.87 (Human Simulacra) | **≥ 0.90** |

Character.ai가 EC에서 높은 이유는 실제 공인(public figures)을 페르소나로 쓰기 때문.
우리는 실존 기관 기반 개인 페르소나로 EC를 경쟁력 있게 유지하면서 IC와 RC를 강점으로 삼는 전략.
